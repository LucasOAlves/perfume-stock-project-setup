# Learnings — Slice 3 Implementation (Reservations + Concurrency)

## The concurrency test is real, not theoretical

`test/integration/reservations.test.ts`'s "allows exactly one of two concurrent reservations for the last unit to succeed" test fires two `Promise.all`-parallel HTTP requests at the same product with `on_hand_quantity = 1`. This only proves anything because Fastify's `.inject()` and the underlying Postgres driver actually interleave the two requests' transactions — verified by running it 5 times in a row with zero flakiness. The mechanism: both transactions issue `SELECT ... FOR UPDATE` on the same product row; the second to arrive blocks until the first commits, then re-reads `on_hand_quantity`/`reserved_quantity` post-lock and correctly finds no room left. This is exactly what [ADR-002](../decisions/ADR-002-reservation-concurrency.md) predicted — worth treating any future change to this locking pattern as requiring a re-run of this specific test under real concurrency, not just a passing typecheck.

## Reservation expiry: lazy sweep scoped to the product being touched, not a cron job

Per `docs/plans/mvp.md`, expiry doesn't get a background job in the MVP. The actual implementation: `sweepExpiredReservations()` (in `reservations.service.ts`, exported for reuse) runs at the top of every transaction that already holds the product row lock — `createReservation`, `cancelReservation`, and `InventoryService.fulfillReservation` all call it right after acquiring the lock, before doing anything else. This is safe without a lock on the reservation rows themselves *only* because all reservation-affecting operations for a given product are serialized through that one product-row lock — a reservation row is never mutated by two transactions at once because they'd have to hold the same product lock first.

**Known, accepted limitation**: `GET /networks/:id/products` (the list view) does **not** sweep — it just returns the last-computed `reserved_quantity`. If a reservation expires and nobody creates/cancels a reservation or records a stock movement for that specific product afterward, the list view can under-state availability (show a unit as reserved when it's actually expired) until the next write touches that product. This is deliberately the safe direction to be wrong in — it never lets two sellers over-promise, it only occasionally makes an available unit look unavailable for a while. If this becomes a real UX complaint, the fix is a scheduled sweep job, not a redesign of the locking model.

## Cross-module import: `sweepExpiredReservations` and `fulfillReservation`

`InventoryService.fulfillReservation` needs to read/write both `ProductEntity` and `ReservationEntity` in one transaction (a `SALE_FROM_RESERVATION` movement must close the reservation and decrement stock atomically — see `docs/product/domain-model.md` invariant 3). Per [ADR-001](../decisions/ADR-001-architecture-style.md), module boundaries in this codebase are organizational, not enforced by the type system — so `inventory.service.ts` directly imports `sweepExpiredReservations` from `reservations.service.ts` and constructs/queries `ReservationEntity` rows itself. This is a deliberate, narrow exception for one genuinely cross-cutting operation, not a precedent for routinely reaching across module folders — if this pattern starts recurring elsewhere, it's a signal the module boundaries themselves need rethinking, not that reaching across is fine everywhere.

## Idempotency key: header, not body field

`createReservation` requires a client-supplied `Idempotency-Key` header (not a body field) — this matches the conventional HTTP idempotency-key pattern and keeps the request body schema (`{ quantity }`) about the actual reservation, not about retry semantics. Enforced with a unique-per-membership partial index (`uq_reservations_idempotency` — unique on `(created_by_membership_id, idempotency_key)` where the key is non-null), so two different sellers can safely reuse the same client-generated key value without colliding. `cancelReservation` deliberately does **not** need an idempotency key: cancelling an already-cancelled reservation just returns 200 with the current (cancelled) state instead of erroring, which makes cancel naturally idempotent without any extra machinery.

## Frontend: `quantitiesChanged` reuse across three different mutation paths

`StockMovementsPanelComponent` emits the same `quantitiesChanged` event whether the on-hand/reserved numbers changed because of a stock movement, a reservation fulfillment, or (from `cancelReservation` inside the same panel) a reservation cancellation. The cancel path computes the new numbers client-side from the reservation's known quantity rather than re-fetching the product, since the server doesn't return updated product numbers from the cancel endpoint (only the reservation). This is a minor optimistic-update spot worth remembering if a future change makes the cancel response shape richer — it'd be more consistent to have the server return the fresh product numbers there too, matching what `recordMovement` and `fulfillReservation` already do.

Verified end to end: 34/34 backend tests passing (11 new for Slice 3) against real PostgreSQL, including 5 repeated runs of the concurrency test with no flakiness; full browser walkthrough — seller reserves a unit, "Minhas reservas" shows it, owner's product panel shows the same active reservation and on fulfillment correctly shows on-hand 6→5, reserved 1→0, available unchanged at 5, with the `SALE_FROM_RESERVATION` movement appearing in history.
