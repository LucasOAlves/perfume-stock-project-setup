# Learnings — Product Naming, Theming, and Language Review

## The real bug: server error messages silently override the frontend's Portuguese text

`extractErrorMessage()` (`apps/web/src/app/core/error-message.ts`) prefers the API's `error.message` over the Portuguese fallback string passed at each call site — that's the correct design (the server knows the specific reason a request failed), but it meant every one of the ~35 `throw new ValidationError(...)`/`ConflictError`/`NotFoundError`/etc. messages across the API was showing up verbatim in the UI, and every one of them was written in English during initial implementation. The Angular templates were fully Portuguese from the start; the actual error text a user would see on almost any failure path was not. This is the kind of bug that's invisible unless you deliberately trigger error states while reviewing — the happy path looked completely correct.

Fixed by translating every thrown message across `identity.service.ts`, `networks.service.ts`, `catalog.service.ts`, `inventory.service.ts`, `reservations.service.ts`, `reservations.routes.ts`, `shared/errors.ts` (default messages), `shared/auth-plugin.ts`, and `shared/membership-guard.ts`. Also added Portuguese label maps for enum-like values that get interpolated into messages — `CAPABILITY_LABELS` (`entities/capability.ts`), `STOCK_MOVEMENT_TYPE_LABELS` (`entities/stock-movement.entity.ts`), `RESERVATION_STATUS_LABELS` (`entities/reservation.entity.ts`) — each with an explicit comment pointing at the frontend copy it must stay in sync with, since these exist in both places by necessity (frontend needs them for its own UI labels; backend needs them to build translated error strings) and there's no shared package between the two apps to hold one source of truth.

**Lesson for future slices**: any new `throw new ValidationError("...")` (etc.) must be written in Portuguese from the start — it is not internal/log-only text, it is the literal string a real user reads on screen. Grep for `throw new (ValidationError|ConflictError|ForbiddenError|NotFoundError|RateLimitedError)\(` before considering a slice done if there's any doubt.

## Zod's built-in validation messages needed a global fix, not per-schema patches

Even after translating every explicit `throw`, Zod's own default messages ("String must contain at least 8 character(s)", "Required", "Invalid uuid") were still reaching the client as-is — Zod schema validation happens before application code runs, and `app.ts`'s error handler passes `ZodError` issue messages straight through as the `ValidationError` text. Patching every `.min()`/`.max()`/`.uuid()`/`.url()` call across every route schema individually would be high-effort and easy to miss on the next new schema. Instead, added one global error map (`apps/api/src/shared/zod-pt-br.ts`, installed once via `z.setErrorMap()` at the top of `app.ts`) covering the issue codes actually used in this codebase (`invalid_type`, `too_small`, `too_big`, `invalid_string`, `invalid_enum_value`, `custom`). Verified live: submitting a 4-character phone number now shows "Deve ter pelo menos 8 caractere(s)" instead of the English default.

## Design tokens had to be renamed, not just re-valued

Redesigning the palette for `docs`-requested dark mode support required converting every hardcoded color reference (`--primary-color`, `--text-color`, etc. plus a few literal hex values like `#ede9fe` for the "Dono" tag) into a `--color-*` token namespace with light-default / `prefers-color-scheme` / `[data-theme]` layering — the same three-layer pattern used for artifact theming. Two literal hex duplicates (`.owner-tag` defined identically in both `networks-page.component.ts` and `members-page.component.ts`) were consolidated into one shared global `.tag` class in `styles.css` rather than kept as two component-local copies, since a token-based color can't be dark-mode-correct if it's hardcoded per-component.

## Theme toggle: three states, not two

The user explicitly asked for both "the user can choose" and "and also match the phone's setting" — a plain light/dark toggle can't do both at once (once toggled, it stops following the OS). `ThemeService` (`apps/web/src/app/core/theme.service.ts`) implements a three-way `system | light | dark` preference, defaulting to `system`, persisted to `localStorage`, cycling via one header button (🖥️ → ☀️ → 🌙 → 🖥️). `system` mode removes the `data-theme` attribute entirely (letting the CSS `prefers-color-scheme` media query govern) rather than reading `matchMedia` in JS and setting an explicit value — that way an explicit "light" choice while the OS is dark, or vice versa, both work correctly by construction, verified in the browser via `resize_window`'s `colorScheme` emulation in both directions.

## Product naming: split user-facing from internal codename, deliberately

"Shared Stock" (English) remains the repo name, npm package names, database names, and every doc under `docs/`/`.agents/` — only the actual running app (browser title, `<html lang>`, header brand, and now every error string) uses "Estoque Vivo." This was a deliberate scope decision (not fully executed automatically) to avoid a large low-value rename across the entire engineering surface for a decision that only needs visibility in the product itself — documented in `docs/product/product-spec.md` under "Product Naming" and in the README's opening lines, specifically so a future reader doesn't find the mismatch confusing or assume it's an oversight.

Verified end to end: 44/44 backend tests still passing after every message change (tests assert status codes, not message text — none needed updating); full browser walkthrough across light/dark/system themes and multiple pages; live confirmation that both custom `ValidationError` messages and Zod's built-in validation messages now render in Portuguese.
